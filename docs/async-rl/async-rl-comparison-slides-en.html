How Is Generated Data Staged?

Starting point of an RL step: the inference engine generates rollouts, data enters the buffer awaiting training consumption

Three Buffer Strategies

SLIME: Double-Buffer

1
Buffer Depth
  • Main loop directly schedules rollouts
  • At most 1 batch in-flight
  • Gen N+1 overlaps with Train N
  • Scheduling logic ~40 lines

NeMo-RL: Replay Buffer

1~N
Buffer Depth (configurable)
  • Background Collector generates continuously
  • Training pulls data from Buffer on demand
  • Target weight version matching
  • Stall semantics: wait if insufficient

verl: Bounded Queue

N
Queue Depth (staleness-driven)
  • Independent Rollouter actor streaming
  • Per-sample granularity push into queue
  • When full, drop old data; never block producer
  • Two-level backpressure control
Key distinction: SLIME's buffer depth is fixed at 1 (at most 1-step staleness); NeMo-RL configures depth via max_trajectory_age_steps; verl indirectly controls queue capacity via staleness_threshold.

② Partial Rollout

What Happens When Generation Is Interrupted?

Weight sync or oversampling completion during rollout → what happens to in-flight requests?

Partial Rollout: Three Strategies

NeMo-RL: Not Supported

  • All samples must run to completion
  • No abort / recycle mechanism
  • In-flight mode does not terminate ongoing generation

SLIME: Abort + Recycle

  • Abort remaining requests once train batch is filled
  • Already-generated tokens from aborted requests go to recycle buffer
  • Next round prioritizes pulling partial samples from buffer
  • Old tokens get loss_mask=0
Advantage: No wasted work + can leverage prefix cache

verl: Abort + Prefix Continue

  • Hard abort engines, then retry each aborted request in a loop
  • Input prompt += already-generated tokens, continue generating
  • Fully transparent to upper-level callers, unaware of abort
Cost: KV cache is cleared, cannot leverage prefix cache

Layer 2: How Is the Loss Corrected?

This is where TIS / OPSM / mask-IS / seq-mask-TIS are compared. They address the off-policy drift "after samples have entered the trainer."

Token-level Correction

StrategyFormulaFramework
TIS clamp(πθ/πold, max=T) SLIME NeMo-RL verl
Mask-IS / Rejection ratio exceeds limit → zero out or mask NeMo-RL verl

Sequence-level Correction

StrategySeq MetricTrigger ConditionFramework
OPSM seq_kl = mean(log π_old - log π_cur) adv < 0 and seq_kl > δ → mask SLIME
seq-mask-TIS geo-mean IS = exp(mean(log π_old - log π_rollout)) geo-mean IS outside [min,max] → mask NeMo-RL
Rejection seq_sum/mean/max of k1/k2/k3(log-ratio) sequence divergence statistic exceeds threshold → mask verl
Common thread: All three start from token-level log-prob difference / log-ratio, aggregate into a sequence scalar, then decide whether to mask.
SLIME stays in log-space; NeMo-RL takes exp to get a geometric mean IS ratio; verl transforms the log-ratio into k1/k2/k3 divergence statistics for rejection.

④ Weight Sync Protocol

How Are New Weights Pushed to Inference Engines?

Training completes → new weights need to be synced to inference GPUs → this is the final step of an RL iteration

Weight Sync: Three Interruption Strategies

SLIME: Drain → Sync

① Outer scheduler drains in-flight rollout first
② pause_generation
③ flush KV cache
④ TP all-gather
⑤ Megatron → HF format conversion
⑥ Bucketed NCCL broadcast
⑦ continue_generation

Requires HF format conversion + lock coordination

NeMo-RL: Pause → Sync

① Pause new generation
② (Blocking) wait for pending to finish
   (In-flight) skip waiting
③ NCCL collective broadcast
   via vLLM collective_rpc
④ (Optional) invalidate KV cache
⑤ version++ + resume generation

No format conversion needed, vLLM receives directly

verl: Abort → Sync

① Hard abort all requests
② Sleep replicas (release KV memory)
③ Establish NCCL communicator group
④ Bucketed NCCL broadcast
⑤ Destroy communicator group
⑥ Wake replicas (restore engine / reclaim KV memory)
⑦ Resume generation

Memory borrowing: sleep frees KV space for the buffer

NeMo-RL's In-flight Weight Update is a unique aggressive feature: weight sync does not wait for in-progress generation to complete, allowing some tokens to be generated with old weights and others with new weights. This relies on vLLM V1's collective_rpc capability. Optionally combined with KV cache invalidation to mitigate inconsistency.

Key Takeaways

1. Three Design Philosophies, One Core Trade-off

SLIME chooses simplicity (double-buffer + 40-line main loop); NeMo-RL chooses aggressiveness (in-flight weight update + deep replay buffer); verl chooses generality (fully decoupled independent actor architecture). But fundamentally, all are balancing GPU utilization vs. off-policy drift.

2. Buffer Depth Is the Key Knob

SLIME fixes it at 1 step (safest); NeMo-RL and verl allow multiple steps (higher throughput). NeMo-RL's official configs already have max_trajectory_age_steps=8 instances for MoE 24-node scenarios. The deeper the buffer, the more critical version filtering / staleness handling becomes — not just loss-layer correction.

3. No Silver Bullet for Staleness Correction

All three frameworks use IS correction, but the real difference lies in whether there is filtering / selection before the loss: SLIME's default path constrains lag with depth=1, then applies TIS/OPSM; NeMo-RL uses target-match + age-window to decide which samples enter the current step, then applies IS; verl combines queue threshold, rejection, and MIS more systematically. Which is better depends on the degree of staleness and the system complexity budget.

4. Weight Sync Is the Biggest Engineering Bottleneck

The three frameworks diverge most on weight sync: SLIME needs format conversion + lock coordination; NeMo-RL leverages vLLM's collective_rpc for the simplest path; verl's sleep/wake memory borrowing is the most flexible. The interruption strategy (drain/pause/abort) directly determines how partial rollouts are handled.
